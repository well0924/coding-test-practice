2.문제 해결 과정

![Image](https://github.com/user-attachments/assets/82041097-308d-41b8-a79c-5791a2e9de88)

이 문제의 요구사항은 문제의 입력값을 보면 직관적으로 알 수 있는 문제입니다.

맨 처음에 K라는 정수(1<= K <=100,000)를 입력을 하고 K만큼 반복문을 돌리면서 기존의 숫자를 입력을 하면서 기존의 숫자를 저장을 하고 정수0이 나오면 가장 마지막에 입력했던 숫자를 없애는 방식으로 진행을 하고 최종적으로 남아있는 숫자를 다 합쳐서 출력을 하면 되는 문제입니다. 

 이 문제를 풀기 위해서 사용이 된 자료구조는 스택입니다. 문제의 예시를 보면 K만큼의 숫자를 입력을 하면서 0이 나오면 가장 최근에 들어온 숫자를 제거를 하는 방식이므로 후입선출인 스택을 사용을 하는 것이 타당해서 스택을 선택을 했습니다. 

또한 입력값의 범위를 보면 $K$가 최대 100,000이기 때문에, 매번 삭제 연산이 일어날 때마다 배열 전체를 탐색하거나 재배치하면 성능 문제가 생길 수 있습니다. 스택의 `push`와 `pop`은 모두 $O(1)$이므로 전체 로직은 $O(K)$ 안에 끝나야 하는 것을 알수가 있습니다. 

이렇게 도출이 된 내용을 토대로 해서 작성한 의사코드는 아래와 같습니다. 

![Image](https://github.com/user-attachments/assets/7b4b25ff-5f9f-4fc6-a559-f9f2c7cb1b3e)

코드의 흐름은 아래와 같습니다.

1. BufferedReader를 사용해서 입력값num을 선언
2. Stack과 결과값인 sum변수를 선언
3. 반복문을 사용해서 num만큼 돌리면서 입력값이 0인경우에는 pop을 아닌 경우에는 push를 한다.
4. 스택에 저장된 정수를 sum 변수에 더한다.
5. 최종값을 출력을 한다.

이를 토대로 한 로직의 플로우와 작성한 코드는 아래와 같습니다.

<img width="855" height="692" alt="Image" src="https://github.com/user-attachments/assets/ca0b02f7-81f2-461b-bff8-d2823fbc9e89" />

```
public static void main(String[] args) throws IOException {
	BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
		
	int num = Integer.parseInt(br.readLine());
		
	Stack<Integer>stacks = new Stack<Integer>();
	int sum = 0;
		
	for(int i= 0; i<num; i++) {
		int input = Integer.parseInt(br.readLine());
			
		if(input==0) {
			stacks.pop();
		} else {
		stacks.push(input);
		}
	}
		
	while (!stacks.isEmpty()) {
		sum += stacks.pop();
	}
	System.out.println(sum);		
}
```

3.타인 코드 분석 및 리팩토링

문제를 제출하고 이번에도 타인이 제출한 코드의 유형을 봤습니다. 유형은 대체적으로 2가지 입니다.

- 자바에서 제공하는 라이브러리를 최소화해서 성능을 최대화한 코드(그림1,2)
- 배열을 사용한 코드(그림3)

3-1. 가장 낮은 수준(Low-level)의 API를 직접 구현하여 속도를 극대화한 유형(그림1,2)

<img width="670" height="633" alt="Image" src="https://github.com/user-attachments/assets/43f10a8b-3024-413d-8949-e5fdc109575f" />

- 분류 기준
    - **입출력:** `System.in.read()`를 사용해 바이트 단위로 읽어 숫자를 직접 파싱(`read()`, `nextInt()`).
    - **저장 방식:** `int[]` 배열과 인덱스 포인터(`top`, `now`)를 사용해 스택을 직접 구현.
- **특징 분석**
    - **비트 연산 활용:** `n = (n << 3) + (n << 1) + (c & 15)` 처럼 곱셈 연산조차 비트 이동으로 처리하여 CPU 연산 횟수를 줄였습니다.
    - **가장 빠름:** `BufferedReader`보다도 수 배 이상 빠르며, 메모리 낭비가 거의 없습니다.
        
- **장단점**
    - **장점:** 백준 랭킹 상위권 진입 가능.
    - **단점:** 코드가 난해하여 로직 가독성이 떨어지며, 현업 실무에서는 유지보수가 불가능에 가깝습니다.

3-2.표준적인 성능 최적화 도구를 사용하면서도 내부 로직을 직접 관리하는 유형

<img width="878" height="595" alt="Image" src="https://github.com/user-attachments/assets/e80ad10e-ddfd-4f32-89e2-9023b0fc96b9" />

- **분류 기준**
    - **입출력:** `BufferedReader`와 `Integer.parseInt()`를 사용.
    - **저장 방식:** `int[]` 배열 스택 직접 구현 + **실시간 합산 로직**.
- **특징 분석**
    - **실시간 합산:** 마지막에 스택을 다시 돌며 합을 구하는 대신, `push`할 때 더하고 `pop`할 때 빼는 방식을 사용하여 루프를 한 번 줄였습니다.
    - **현실적인 최적화:** `System.in.read()`보다는 느리지만, `Scanner`보다는 월등히 빠르며 코드의 가독성도 어느 정도 챙겼습니다.
- **장단점**
    - **장점:** 구현이 명확하고 빠릅니다. 백엔드 개발자가 알고리즘 시험에서 가장 흔히 채택하는 방식입니다.
    - **단점:** 여전히 `Stack` 클래스 같은 표준 API를 쓰지 않으므로 '의도'를 파악하는 데 약간의 시간이 필요합니다.


4.소감

기존의 스택과 관련된 문제인 괄호를 풀면서 스택 문제에 대해서 조금 더 익숙해지는 문제였습니다. 하지만 이번 풀이는 단순히 "정답을 맞혔다"는 결과보다, **엔지니어로서 코드를 객관적으로 점검하고 개선하는 과정**에 집중했다는 점에서 더 큰 의미가 있었습니다.

첫째로, **데이터 범위에 따른 자료형 선택의 중요성**을 체감했습니다. 문제의 조건을 분석했을 때 $K$가 10만이고 입력값이 100만인 점을 고려하면, 합계가 약 1,000억에 달해 `int` 범위를 초과할 수 있다는 점을 파악했습니다. 최종 합산 변수를 `long` 타입으로 고려하는 습관은 백엔드 개발자로서 데이터 무결성을 지키기 위한 가장 기본적이면서도 치명적인 실수(Overflow)를 방지하는 중요한 연습이 되었습니다.

둘째로, **타인의 코드를 분석하며 '성능과 가독성의 트레이드오프'를 깊이 있게 고민했습니다.** 직접 배열을 관리하는 방식들을 비교하며, 무조건적인 라이브러리 사용보다는 상황에 맞는 최적의 도구를 선택하는 '근거 있는 개발'의 필요성을 배웠습니다. 특히 입력과 동시에 합계를 관리하여 루프를 줄이는 최적화 기법은 실무에서 대량의 데이터를 처리할 때 참고할 만한 좋은 인사이트였습니다.

단순히 문제를 푸는 것에서 끝내지 않고 **"왜 이 방식을 선택했는가?"**를 끊임없이 질문하며 더 나은 방향으로 개선해 나가는 과정 자체가 큰 성취감이었습니다.
